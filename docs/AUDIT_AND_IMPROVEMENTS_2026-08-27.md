## 1. 반품 처리 성공 판정 오류

**위치**: `src/components/OrderManagePage/ReturnListPanel.tsx:220`, 일괄처리 부분

### 문제
`confirmReturn()`이 API 오류를 내부에서 잡고 종료합니다. 그런데 일괄처리 함수는 함수가 정상 종료되면 성공으로 계산합니다.

즉, 실제로는 실패했는데 화면에는 다음과 같이 표시될 수 있습니다.
```
10개 반품확정 완료
```
실제로는 3개만 성공했을 가능성이 있습니다.

### 1차 대응
- API 처리 함수는 성공 시 `true`, 실패 시 throw 또는 명시적인 실패 결과 반환
- 일괄 처리에서는 `Promise.allSettled()` 기준으로 성공·실패를 각각 집계
- 성공 건수와 실패 건수를 모두 표시

예시 결과: `성공 7건 / 실패 3건`

### 2차 대응
- 실패한 상품코드와 실패 사유를 별도 목록으로 저장
- 재시도 버튼 제공
- 서버에서도 요청별 처리 결과를 반환
- "전체 성공"은 모든 요청이 실제 완료된 경우에만 표시

### 검증방법
- 정상 요청 3건 · 네트워크 오류 1건 · 서버 500 오류 1건 · 중복 요청 1건
- 각 경우에 화면의 성공·실패 건수가 실제 API 결과와 일치해야 함

## 2. 반품 생성과 확정이 분리되어 중간 데이터가 남음

**위치**: `src/components/OrderManagePage/ReturnListPanel.tsx:225`, `server/routes/purchase/returnRequests.ts:24`

### 문제
현재 처리는 다음 순서입니다.
1. POST로 pending 생성
2. PATCH로 done 변경

1번은 성공하고 2번이 실패하면 DB에는 pending 데이터가 남습니다. 사용자가 다시 누르면 동일 상품에 반품 요청이 하나 더 생길 수 있습니다.

### 1차 대응
- 반품 확정용 API를 별도로 만들고 서버에서 한 번에 처리
- 생성 시 최종 상태까지 전달
- 이미 같은 상품에 처리 중인 요청이 있으면 중복 생성 차단
- 예시 조건: 같은 `product_code` + `pending`/`done` 상태가 있으면 중복 요청 금지

### 2차 대응
- DB 트랜잭션 적용
- product_code, 처리 기준일, 상태를 기준으로 중복 방지 정책 추가
- 실패한 요청은 `failed` 상태로 남겨 운영자가 확인 가능하게 구성
- 자동 재시도 시 같은 요청을 다시 생성하지 않고 기존 요청을 재사용

### 검증방법
- POST 성공 후 PATCH 실패 상황을 강제로 발생
- 재시도 후 행이 2개 생기지 않는지 확인
- 화면 목록과 DB의 상태가 일치하는지 확인

## 3. 반품 API의 세부 권한이 부족함

**위치**: `server/routes/purchase/returnRequests.ts:24, 113, 144`

### 문제
`server.ts:201`에서 전체 API에 로그인 검사는 적용됩니다. 하지만 반품 API 중 다음 요청에는 `authorize()`가 없습니다.
- 반품 생성 POST
- 반품 수량·사유·상태 변경 PATCH
- 일괄 발송 POST

반면 삭제만 `authorize(2)`가 적용되어 있습니다.

따라서 정책상 제한이 필요하다면, 일반 로그인 사용자도 반품 상태를 변경하거나 발송 처리할 수 있습니다.

### 1차 대응
API별 최소 권한을 명확히 정해야 합니다.

권장 예시:
- 반품 조회: 로그인 사용자
- 반품 생성: level 2 이상
- 반품 수정: level 2 이상
- 반품 발송: level 5 이상
- 반품 삭제: level 9 이상

### 2차 대응
- 본인이 생성한 요청인지 확인하는 소유권 검사 추가
- 관리자는 전체 접근
- 일반 사용자는 본인 요청만 수정
- 모든 상태 변경에 감사 로그 기록

### 검증방법
- level 1, level 2, level 5, level 9 계정별 API 테스트
- 직접 URL 호출로 권한 우회가 가능한지 확인
- 프론트 화면에서 버튼을 숨겨도 API가 차단되는지 별도 확인

## 4. 입력값 검증이 프레임워크 표준과 다름

**위치**: `server/routes/purchase/returnRequests.ts:25`

### 문제
현재는 다음과 같은 수동 변환을 사용합니다.
```typescript
Number(b.qty ?? 0) || 0
String(b.product_code ?? "").trim()
```

이 방식은 다음 오류를 통과시킬 수 있습니다.
- 음수 수량
- 지나치게 큰 수량
- 잘못된 상태값
- 존재하지 않는 상품코드
- 문자열로 전달된 비정상 숫자
- 허용하지 않은 필드

### 1차 대응
zod 스키마를 만들고 `validateBody()`를 적용해야 합니다.

검증 항목:
- `product_code`: 필수 문자열
- `qty`: 1 이상 정수
- `status`: `pending`/`sent`/`done`/`cancelled` 중 하나
- `reason`: 최대 길이 제한
- `requested_by_id`: 양의 정수

### 2차 대응
- 상품코드가 실제 상품 테이블에 존재하는지 서버에서 확인
- 재고보다 많은 반품 수량 차단
- 상태 변경 규칙 정의

예시:
- `done -> pending` 변경 금지
- `cancelled -> done` 변경 금지
- `sent -> pending` 변경 금지

### 검증방법
- 잘못된 JSON · 음수 수량 · 허용되지 않은 status · 긴 문자열 · 추가 임의 필드 · 존재하지 않는 상품코드
- 모두 400 응답으로 차단되어야 함

## 5. 반품 조회가 커지면 성능 저하 가능성

**위치**: `server/routes/purchase/returnRequests.ts:56`

### 문제
일반 목록은 최대 2,000건까지 조회하고, 공급사별 요약 API는 기간 내 모든 데이터를 읽은 뒤 서버 메모리에서 그룹화합니다.

반품 이력이 누적되면 다음 문제가 발생할 수 있습니다.
- 응답 속도 저하
- 서버 메모리 증가
- 동시 사용자가 많을 때 처리 지연
- 모바일 화면 로딩 지연

### 1차 대응
- 목록 API에 `page`, `limit` 표준 적용
- 기본 `limit`을 50~100건으로 제한
- `count: exact` 또는 별도 count API 사용
- 공급사별 집계에는 최대 조회 기간 제한

### 2차 대응
- DB View 또는 RPC로 공급사별 집계를 DB에서 수행
- `supplier`, `status`, `created_at` 복합 인덱스 검토
- 오래된 반품 이력 보관 정책 수립

### 검증방법
- 1만 건 이상의 테스트 데이터로 응답시간 측정
- 10명 이상 동시 조회
- 95퍼센타일 응답시간 기록

## 6. 프레임워크 감사 결과가 실제 서버 품질을 모두 보장하지 않음

**위치**: `scripts/audit-framework.cjs:12, 287`

### 문제
현재 감사 스크립트는 `src` 디렉터리를 기준으로 실행됩니다. 따라서 다음 서버 품질은 자동으로 충분히 검사되지 않습니다.
- 서버 API 권한
- Zod 입력 검증
- 감사 로그
- DB 트랜잭션
- 서버 페이지네이션
- 소유권 검사

`npm run audit:check`가 통과해도 서버 라우트의 권한 문제가 발견되지 않을 수 있습니다.

### 1차 대응
프레임워크 감사에 서버 전용 규칙을 추가해야 합니다.

검사 대상: `server/routes/**/*.ts`

검사 규칙:
- 변경 API에 `authorize()` 존재 여부
- POST/PATCH에 `validateBody()` 존재 여부
- 중요 데이터 변경에 `audit()` 존재 여부
- 목록 API에 pagination 적용 여부
- `asyncHandler()` 적용 여부

### 2차 대응
- route 목록 자동 추출
- HTTP method별 정책 검사
- 예외 허용 목록 관리
- baseline에 보안 위반과 유지보수 위반을 별도 저장
- CI에서 보안 위반은 경고가 아니라 실패 처리

## 7. 대형 파일 관리가 아직 부족함

주요 파일:
- `src/components/OrderManagePage/OrderManagePage.tsx`
- `src/components/OrderManagePage/ReturnListPanel.tsx`
- `src/components/OrderManagePage/VendorDetailTabs.tsx`
- `src/components/DisplayPage/DisplayPage.tsx`

### 문제
한 파일에 다음 내용이 함께 들어가는 경우가 많습니다.
- 화면 렌더링 · API 호출 · 상태 관리 · 입력 검증 · 모달 처리 · 데이터 변환 · 업무 규칙

작은 수정도 다른 기능에 영향을 줄 수 있습니다.

### 1차 대응
페이지 단위가 아니라 업무 단위로 분리합니다.

예:
- `ReturnListPanel` · `ReturnRequestTable` · `ReturnRequestActions` · `ReturnRequestService` · `ReturnRequestTypes`

### 2차 대응
- API 호출을 `services` 또는 전용 hook으로 이동
- 업무 규칙은 순수 함수로 분리
- 컴포넌트는 화면 상태와 표시 중심으로 축소
- 500줄 이상 신규 파일은 리뷰 시 분리 사유 기록

### 검증방법
- 컴포넌트 단위 테스트
- API 서비스 단위 테스트
- 기존 화면 동작 비교
- 렌더링 횟수 측정

## 8. 테스트는 많지만 핵심 업무 테스트가 비어 있음

현재 테스트 파일은 다수 존재하지만 `returnRequests` 전용 라우트 테스트는 확인되지 않았습니다.

현재 확인된 테스트는 다음 성격이 많습니다.
- 공통 유틸리티 · 인증 미들웨어 · Zod 스키마 · UI hook · 문자열·날짜 변환

### 1차 대응
반품 업무에 대한 서버 테스트를 먼저 추가해야 합니다.

필수 테스트:
1. 정상 반품 생성
2. 잘못된 수량 거부
3. 권한 없는 상태 변경 거부
4. 존재하지 않는 요청 수정 거부
5. 중복 반품 차단
6. 일괄처리 일부 실패
7. DB 실패 후 재시도

### 2차 대응
- 실제 Supabase를 사용하는 통합 테스트 환경 구성
- 테스트 DB 또는 격리된 스키마 사용
- 주요 업무 흐름은 Playwright 기반 E2E 테스트 추가
